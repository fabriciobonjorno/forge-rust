# PostgreSQL in Forge Applications

Status: Phase 2. This guide covers what the code provides today: configuration,
local development, migrations, repository primitives, pagination, error
mapping, testing and the HTTP helpers. The design rationale is in
[ADR 0007](adr/0007-sqlx-postgresql-first.md) and
[ADR 0010](adr/0010-migrations-and-database-lifecycle.md). Examples use an
application named `shop`.

The building blocks live in the `forge-db` crate, re-exported as `forge::db`
when the `forge` crate's default `postgres` feature is on. `forge-core`
provides `Id<T>`, `Version` and the pagination types (`forge::core`).
[`examples/catalog`](../examples/catalog) is the reference application for
these primitives.

## Configuration

An application declares PostgreSQL with `App::postgres(sqlx::migrate!())`.
Applications generated by `forge new` already do this unless
`--skip-database` is used.

| Variable | Default | Meaning |
| --- | --- | --- |
| `FORGE_DATABASE_URL` | none | `postgres://` or `postgresql://` connection URL. Required by `serve`, `migrate` and `rollback` in an application that calls `App::postgres`, which exit `78` without it. |
| `FORGE_DATABASE_MAX_CONNECTIONS` | `10` | Maximum pooled connections (positive integer). |
| `FORGE_DATABASE_ACQUIRE_TIMEOUT_SECS` | `5` | Maximum wait for a pooled connection, including connecting (positive integer, seconds). |

Validation fails closed, like every other `FORGE_*` variable:

- A URL without a `postgres://` or `postgresql://` scheme is rejected. The
  error message never contains the value.
- Setting either pool variable without `FORGE_DATABASE_URL` is an error.
- The URL is held in a `SecretString`, whose `Debug`, `Display` and `Serialize`
  output is `[REDACTED]`. `Database`'s `Debug` output shows only pool
  statistics.
- An application that does not call `App::postgres` accepts the variable but
  does not use it.

TLS and other connection settings go in the URL query string. See
[deployment](deployment.md#database-tls).

## Local development

With the generated `compose.yaml`, start only the database service, then run
the application on the host:

```sh
docker compose up -d db
export FORGE_DATABASE_URL=postgres://app:app@127.0.0.1:5432/shop_development
forge migrate            # or: cargo run -- migrate
cargo run
curl -i localhost:3000/health/ready
```

The database name is `<name>_development`, with `-` replaced by `_`. The
`app`/`app` credentials are for local development only, and the port is
published on `127.0.0.1` only. Data persists in the named volume `db-data`
until `docker compose down --volumes`.

`docker compose up --build` runs the whole stack: `db` (with a `pg_isready`
health check), then the one-shot `migrate` service (the application image
running `migrate`), then `app` once `migrate` has completed successfully.

`serve` connects lazily. The server starts even when PostgreSQL is down:
`/health/live` answers `200`, `/health/ready` answers `503`, and queries fail
with a retryable error until the database is reachable.

## Migrations

### Creating a migration

Run this in the application directory (the one containing `Cargo.toml`):

```sh
forge generate migration create_products
```

This creates a reversible pair with a UTC `YYYYMMDDHHMMSS` version:

```text
migrations/20260926130405_create_products.up.sql
migrations/20260926130405_create_products.down.sql
```

Names must be snake_case, at most 64 characters: start with a lowercase ASCII
letter, use only lowercase letters, digits and `_`, and do not end with `_` or
repeat `_`. The command creates `migrations/` if needed and never overwrites
an existing file.

Write the forward change in `.up.sql` and its exact inverse in `.down.sql`:

```sql
-- 20260926130405_create_products.up.sql
CREATE TABLE products (
    id uuid PRIMARY KEY,
    name text NOT NULL CONSTRAINT products_name_not_blank CHECK (length(name) > 0),
    version bigint NOT NULL DEFAULT 1 CHECK (version >= 1)
);
```

```sql
-- 20260926130405_create_products.down.sql
DROP TABLE products;
```

`sqlx::migrate!()` embeds `migrations/` into the binary at compile time. The
generated `build.rs` makes Cargo rebuild when that directory changes.

### Applying and reverting

| Command | Effect |
| --- | --- |
| `forge migrate` / `<binary> migrate` | Applies every pending migration in version order and logs each applied version. Nothing pending is a success. |
| `forge rollback` / `<binary> rollback` | Reverts only the most recently applied migration (the highest applied version) and logs it. Nothing applied is a success. Run it again to revert further. |

`forge migrate` and `forge rollback` run `cargo run --quiet -- migrate` and
`cargo run --quiet -- rollback` in the current directory. In a deployment, run
the binary directly (see [deployment](deployment.md#running-migrations)).
`serve` never applies migrations.

Rules enforced by the runner:

- **Serialized.** Both commands hold SQLx's PostgreSQL advisory lock for their
  whole run, so concurrent runners (several init containers, for example) wait
  for each other instead of racing.
- **Checksummed.** Applied migrations are recorded in `_sqlx_migrations` with a
  checksum. If an applied migration's file has changed, `migrate` fails
  (`VersionMismatch`). If an applied migration is missing from the binary, it
  also fails (`VersionMissing`).
- **Transactional.** Each migration runs in its own transaction, unless the
  file starts with `-- no-transaction`. That is needed for statements such as
  `CREATE INDEX CONCURRENTLY`, which PostgreSQL does not allow inside a
  transaction. The check applies to the very first line, so replace the
  generated comment header rather than adding the directive below it.
- **Reversible or refused.** `rollback` of a migration without a `.down.sql`
  fails with `IrreversibleMigration` (exit `1`) and changes nothing.

Released migrations are immutable. Once a migration has run anywhere outside
your machine, change the schema with a new migration. Editing an applied
migration breaks its checksum. `rollback` is meant for iterating on an
unreleased migration and for deliberate operator reverts. A down migration can
destroy data, so review it like any other migration.

## Repositories

SQL stays visible. Repository port traits live in `src/application/ports`, and
their PostgreSQL implementations live in `src/adapters/persistence`, with SQL
written directly against the re-exported SQLx (`forge::db::sqlx`). The
generated `tests/architecture.rs` rejects `sqlx` imports in `src/domain` and
`src/application`. It does not currently reject `forge::db`, so keep database
types out of those rings by convention.

`sqlx::migrate!()` and `#[derive(sqlx::FromRow)]` expand to `::sqlx` paths, so
the application keeps `sqlx` as a direct dependency. Generated applications
already have it.

### Wiring

The pool is created by `App` and handed to the composition root:

```rust
pub fn run() -> ExitCode {
    forge::App::new(env!("CARGO_PKG_NAME"))
        .version(env!("CARGO_PKG_VERSION"))
        .postgres(sqlx::migrate!())
        .compose(|composition| {
            let database = composition.database()?.clone();
            let products = crate::adapters::persistence::PgProducts::new(database);
            // build use cases with `products` and register routes
            composition.router().route(/* ... */)?;
            Ok(())
        })
        .run()
}
```

`Composition::database()` fails with `ComposeError::DatabaseNotDeclared` unless
the application called `App::postgres`. `Database` is cheap to clone and shares
the pool.

### Typed identifiers and versions

With the `sqlx` feature of `forge-core` (enabled by `forge-db`):

- `Id<T>` binds and decodes as PostgreSQL `uuid`. Decoding rejects UUIDs that
  are not version 7 with a decode error instead of producing an invalid id.
- `Version` binds and decodes as `BIGINT`. Decoding rejects values below `1`.

```rust
use forge::core::{Id, Version};
use forge::db::{Database, DbError, expect_rows, sqlx};

pub enum Product {}

#[derive(sqlx::FromRow)]
struct ProductRow {
    id: Id<Product>,
    name: String,
    version: Version,
}

#[derive(Clone)]
pub struct PgProducts {
    database: Database,
}

impl PgProducts {
    pub fn new(database: Database) -> Self {
        Self { database }
    }

    pub async fn insert(&self, id: Id<Product>, name: &str) -> Result<(), DbError> {
        sqlx::query("INSERT INTO products (id, name, version) VALUES ($1, $2, $3)")
            .bind(id)
            .bind(name)
            .bind(Version::INITIAL)
            .execute(self.database.pool())
            .await?;
        Ok(())
    }

    /// Optimistic locking: succeeds only if nobody changed the row since `seen`.
    pub async fn rename(
        &self,
        id: Id<Product>,
        seen: Version,
        name: &str,
    ) -> Result<Version, DbError> {
        let next = seen.next().map_err(|_| DbError::Conflict)?;
        let result = sqlx::query(
            "UPDATE products SET name = $1, version = $2 WHERE id = $3 AND version = $4",
        )
        .bind(name)
        .bind(next)
        .bind(id)
        .bind(seen)
        .execute(self.database.pool())
        .await?;
        expect_rows(result, DbError::Conflict)?;
        Ok(next)
    }
}
```

`expect_rows(result, on_zero)` returns `on_zero` when the statement affected no
rows. Pass `DbError::Conflict` for version-checked updates and
`DbError::NotFound` for updates or deletes by id. With a version check, zero
rows can mean either a stale version or a missing row. If the difference
matters to the caller, check existence in the same transaction.

### Transactions

`Database::begin` returns a `forge::db::Transaction`. Commit it explicitly.
Dropping it without `commit`, for example on an early `?` return, rolls it
back.

```rust
use forge::db::{advisory_key, advisory_xact_lock};

let mut tx = self.database.begin().await?;
advisory_xact_lock(&mut tx, advisory_key("billing:close-day")).await?;
sqlx::query("UPDATE accounts SET closed_on = CURRENT_DATE WHERE closed_on IS NULL")
    .execute(&mut *tx)
    .await?;
tx.commit().await?;
```

- `advisory_xact_lock(&mut tx, key)` runs `pg_advisory_xact_lock`. It waits
  until no other transaction holds the key, and the lock is released at commit
  or rollback.
- `advisory_key(name)` derives a stable `i64` key: the 64-bit FNV-1a hash of
  the name's UTF-8 bytes. Every instance and release agrees on it.

Forge does not provide a generic unit-of-work port yet
([ADR 0010](adr/0010-migrations-and-database-lifecycle.md#persistence-primitives-now-generic-unit-of-work-later)).
When a use case needs several writes to be atomic, expose them as one port
method and open a single transaction inside the PostgreSQL adapter. Do not pass
a `Transaction` into application code, and do not make network calls while a
transaction is open.

## Pagination

Cursor (keyset) pagination uses UUIDv7 ids, which sort by generation time:

- `PageLimit::new(n)` accepts `1..=100` (`PageLimit::MAX`). Anything else is a
  `Validation` error with code `invalid_page_limit`. `PageLimit::DEFAULT` is
  `20`.
- `PageRequest<T> { limit, after }`: `after` is the previous page's cursor, or
  `None` for the first page.
- `limit.fetch_size()` is `limit + 1`. Fetching one extra row reveals whether a
  next page exists.
- `Page::from_overfetched(rows, limit, id_of)` keeps at most `limit` rows and
  sets `next_cursor` to the last kept id when there were more. `Page`
  serializes as `{"items":[...],"next_cursor":"<uuid>"|null}`.

```rust
use forge::core::{Page, PageRequest};

let rows: Vec<ProductRow> = sqlx::query_as(
    "SELECT id, name, version FROM products \
     WHERE ($1::uuid IS NULL OR id < $1) \
     ORDER BY id DESC \
     LIMIT $2",
)
.bind(request.after)
.bind(request.limit.fetch_size())
.fetch_all(self.database.pool())
.await?;
let page = Page::from_overfetched(rows, request.limit, |row| row.id);
```

The order is newest first. Rows inserted while a client is paging do not shift
or duplicate items it has already received. For filtered lists, index the
filter column together with the id, for example
`CREATE INDEX ... ON notes (owner_id, id DESC)`. UUIDv7 order follows
generation time only approximately. IDs generated in the same millisecond by
different processes are ordered by their random bits
([ADR 0003](adr/0003-uuidv7-default-identifiers.md)).

## Error mapping

Convert SQLx errors with `?` or `DbError::from`, and convert `DbError` into a
caller-safe `ForgeError` with `ForgeError::from`. Client-facing messages never
contain SQL, driver messages or constraint names. A known constraint name is
attached as `constraint` metadata, and `DbError::constraint()` returns it for
application logic.

| `DbError` | From | `ForgeError` code | HTTP | Retryable |
| --- | --- | --- | --- | --- |
| `UniqueViolation` | SQLSTATE `23505` | `already_exists` | 409 | no |
| `ForeignKeyViolation` | SQLSTATE `23503` | `reference_conflict` | 409 | no |
| `CheckViolation` | SQLSTATE `23514`, `23502` | `constraint_violation` | 422 | no |
| `SerializationFailure` | SQLSTATE `40001`, `40P01` | `transaction_conflict` | 503 | yes |
| `NotFound` | `sqlx::Error::RowNotFound`, `expect_rows` | `not_found` | 404 | no |
| `Conflict` | `expect_rows` | `concurrent_modification` | 409 | no |
| `PoolTimeout` | no connection within the acquire timeout | `database_busy` | 503 | yes |
| `Unavailable` | I/O, TLS, closed pool; SQLSTATE class `08`, `57P01`, `57P02`, `57P03`, `53300` | `database_unavailable` | 503 | yes |
| `Migration`, `IrreversibleMigration` | migration failures | `database_migration_failed` | 500 | no |
| `Configuration` | invalid URL or pool settings | `database_misconfigured` | 500 | no |
| `Query` | anything else | `database_error` | 500 | no |

`DbError::is_retryable()` is true for `SerializationFailure`, `PoolTimeout` and
`Unavailable`. Retry a serialization failure by re-running the whole
transaction. An unreachable server can surface as `PoolTimeout` rather than
`Unavailable`, because SQLx retries connecting until the acquire timeout
expires.

## HTTP helpers

`forge::web` keeps handlers thin:

| Function | Behavior |
| --- | --- |
| `web::json(status, &value)` | Serializes `value` as a JSON response. A serialization failure is logged and becomes an empty `500`. |
| `web::error(&forge_error)` | Renders the error's caller-safe report (`code`, `category`, `message`, `metadata` when non-empty, `retryable`) with its category's status. `5xx` errors are logged with their full cause chain: `Infrastructure` as a warning, others as errors. Sources never reach the client. |
| `web::decode_json::<T>(&request)` | Decodes the JSON body. Malformed input becomes a `Validation` error (`422`) with code `invalid_json`, without the decoder's detail. |

```rust
use forge::{core::ForgeError, http::{Request, Response, StatusCode}, web};

async fn create_product(products: PgProducts, request: Request) -> Response {
    let input: CreateProduct = match web::decode_json(&request) {
        Ok(input) => input,
        Err(error) => return web::error(&error),
    };
    let id = Id::new();
    match products.insert(id, &input.name).await {
        Ok(()) => web::json(StatusCode::CREATED, &ProductView { id, name: input.name }),
        Err(error) => web::error(&ForgeError::from(error)),
    }
}
```

In a real application the handler calls a use case, and the use case calls the
repository port. Category-to-status mapping: `Validation` 422, `NotFound` 404,
`Conflict` 409, `Unauthenticated` 401, `Forbidden` 403, `RateLimited` 429,
`Infrastructure` 503, `Internal` 500.

## Testing

`forge_db::testing::TestDatabase` gives each test its own database:

- `TestDatabase::create(&MIGRATOR)` connects with the administrative URL in
  `FORGE_TEST_DATABASE_URL` (for example
  `postgres://postgres:postgres@127.0.0.1:5432/postgres`), creates
  `forge_test_<uuidv7>`, and applies the migrations. It fails with
  `DbError::Configuration` when the variable is unset. If migrating fails, the
  database is dropped again.
- `database()` returns a `Database` (pool of 5, 10-second acquire timeout).
  `config()` returns its `DatabaseConfig`, for example to start a whole `App`
  against it. `name()` returns the generated name.
- `cleanup()` closes the pool and runs `DROP DATABASE ... WITH (FORCE)`. Call
  it at the end of every test. A test that panics leaves its database behind,
  and the `forge_test_` prefix makes such leftovers easy to find.

Because every test has its own database, tests run in parallel. Tests that
need PostgreSQL are marked
`#[ignore = "requires PostgreSQL (FORGE_TEST_DATABASE_URL)"]`, so a plain
`cargo test` stays hermetic:

```rust
use forge::db::{Migrator, testing::TestDatabase};

static MIGRATOR: Migrator = sqlx::migrate!();

#[tokio::test]
#[ignore = "requires PostgreSQL (FORGE_TEST_DATABASE_URL)"]
async fn renames_with_optimistic_locking() {
    let test_db = TestDatabase::create(&MIGRATOR).await.expect("test database");
    let products = PgProducts::new(test_db.database().clone());
    // ...
    test_db.cleanup().await.expect("cleanup");
}
```

Run them against a disposable server:

```sh
docker run -d --rm --name forge-test-pg -e POSTGRES_PASSWORD=postgres \
  -p 127.0.0.1:5432:5432 postgres:18
export FORGE_TEST_DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5432/postgres
cargo test -- --include-ignored     # everything
cargo test -- --ignored             # only the PostgreSQL tests
```

`TestDatabase` sits behind the `testing` feature of `forge-db`. Framework
crates enable it as a dev-dependency (`forge-db = { ..., features = ["testing"] }`,
as `crates/forge` does). The `forge` facade does not forward this feature yet.
An application can add `forge-db` as a dev-dependency from the same source as
`forge`, with `features = ["testing"]`. Cargo then unifies the feature for
test builds, and `forge::db::testing` becomes available.

Handlers can be unit-tested without a server. Build a request with
`forge::http::Request::new(method, uri, body)`, call the handler, and inspect
`Response::status()`, `headers()` and `body()`.

Framework CI runs the workspace's PostgreSQL tests against a `postgres:18`
service (see the [test strategy](test-strategy.md#postgresql-integration-tests)).
